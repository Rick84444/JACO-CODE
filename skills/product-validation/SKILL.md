# Product validation and launch

Aura owns this mission. Use the existing mission bus, Gameboard, receipts, Continuum and current operator mandate. This is a read-only research and decision skill; no outreach, publish, account creation, client-system writes, purchasing or deployment. An operator can separately authorize those exact actions via the existing gates. Do not create another runtime or agent identity. Do not treat this skill as the commercial clock or use it to expand that clock's marketplace allowlist.

## Objective and time budget
Start from the current working JACO release, not a hypothetical architecture. The priority is an external person completing a useful task and, independently, a first paid deliverable. Do not wait for a 30-day study. Work in bounded cycles: default 60 minutes or the actual shorter mission deadline; spend roughly 10 minutes checking evidence, 20 on demand and alternatives, 20 preparing a concrete next experiment and 10 on the receipt/handoff. These are planning estimates, not a scheduler or permission. If data is unavailable, continue the safe independent track.

## 1. Establish what can be offered today
- Health-check and record actual source revision, release artifact link, model/provider, OS, tool availability and known blockers. Read current repo README/release and actual receipts using already configured read tools; if missing, say unknown.
- Distinguish installed local observation, source inspection, CI, and independent external validation. Never infer one from another. Do not publish secrets, local paths, customer data or private traces.
- A candidate external onboarding must identify exact supported OS, download/installation path, prerequisites, first harmless task, expected result, troubleshooting and teardown. Do not assert a clean install without a fresh target-environment receipt. The operator may authorize a separate clean-install mission; this skill cannot run shell or repo-test.
- Choose ONE technically meaningful proof from an actual run: bounded code fix with tests, recovery from a known fault, or same-model transfer from prior experience. Document input, revision, verified result, failure cases, time, costs and independent oracle. If no qualifying result exists, prepare a reproducible test protocol, label not run. For same-model comparisons use identical model/config, starting state, task, limit and oracle; report all runs, failures and unknown costs. Start with a small held-out set; never claim benchmark leadership from a selected run.

## 2. Find genuine demand
- Record dated public pain signals from issue trackers, developer forums, open-source projects, public requests or job boards. Use public business information only; no harvesting contact lists or evading access restrictions.
- Select one initial target segment: local-model developers, maintainers needing long-running agent work, or small businesses with a specific web problem. Describe trigger, current workaround, expected outcome, and why a person would switch. Do not infer interest from stars.
- Compare at least two free options for product positioning, including applicable OpenHands, Hermes, Letta, existing IDE tools or the actual solution cited by the requester. Record source URL, observation date, license if known, comparable function, and concrete difference that can be tested. Do not claim absent features merely because a README is silent. If an existing free solution solves the problem, narrow the offer or use it for delivery.
- For services, reuse docs/commercial/revenue-mission-001-first-sale.md and aura-first-customer-mission.md. The SEK 4900 price is an unvalidated hypothesis, never an approved public price. Prefer a bounded outcome with explicit acceptance and low delivery risk; compare a free workaround and existing supplier price. Separate customer work from product validation.

## 3. Turn evidence into one next experiment
- Product: target one external install and first completed task, then ten qualified testers. Prepare a safe human-reviewable tester brief: audience, problem, exact start path, task, expected acceptance and how to provide feedback without secrets; identify the one blocker most likely to prevent activation. Choose a channel only after reading its live rules. Hacker News prohibits AI-written/edited text and automation; provide technical evidence and official rules links only, no post or comments. Show HN must be usable; no signup-only launch. For channels that allow AI drafts, follow community-post, disclose affiliation and do not solicit votes, spam, or impersonate users.
- Service: identify up to five suitable publicly listed businesses or inbound leads; for the best one draft a scoped nonbinding pilot, problem evidence, work exclusions, acceptance, estimated hours/cost, price hypothesis and exact approval action. No unsolicited bulk contact and no contacting anyone in this read-only mission.
- Paid agent work: hand off to the signed commercial-opportunity-cycle; do not apply from this skill.
- Prioritize whichever experiment has the shortest credible path to a verified user outcome or paid acceptance at low irreversible cost. Do not create additional features unless identified as a blocker by an actual test, installation or buyer.

## 4. Record and learn
Separate product funnel: eligible visitor (if observed), install attempted, install succeeded, first task completed, repeat user. Service funnel: public demand, qualified conversation, agreed scope, delivered work, accepted work, settled payment. A draft, click, star, listing, agreement or escrow is not revenue. Record denominators, date and evidence; unknown counts remain unknown.
Use the existing mission answer and receipt mechanism; outcome memory belongs to canonical Continuum and must be receipt-linked. Store hypotheses as unverified, negative feedback as negative feedback, and never invent users, test runs, quotes or income. Recheck stale claims. If no safe memory write exists in the current mission, return the structured observations for existing ingestion instead of claiming they were stored.

## Deliverable
Return a decision, evidence table (source/observed date/claim/status), competitor comparison, target persona, one narrow task or pilot, time/cost/risks, concrete launch or customer handoff, the single operator decision if required, and next measurable success criterion. Include what was actually done versus not run. Stop when a human decision is required and no independent work remains; do not busy-loop. A real external user outcome beats a polished plan.
